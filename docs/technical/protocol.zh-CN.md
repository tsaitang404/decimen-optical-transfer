# 协议

## 单向信道问题

屏幕到摄像头的链路没有反向通道：接收端无法请求重传，而且必然丢帧（模糊、刷新跨越、自动对焦）。循环发送帧并祈祷不是办法——丢一帧就要等一整圈它才再出现。

## 喷泉编码

发送端从不直接发送文件的块。每一帧是块的伪随机*子集*的 XOR；子集由帧的序列号确定性地导出，子集大小从 robust-soliton 分布中抽取（[Luby transform 编码](https://en.wikipedia.org/wiki/Luby_transform_code)）。接收端按任意顺序收集**任意**约 K·1.15 个不同帧，就能把文件剥出来。丢帧只损失一点时间，绝不损失正确性；发送端和接收端的帧率不必一致。

发送端和接收端必须构建**比特级一致**的 soliton 分布，而 JS 引擎对 `Math.log` 的实现有分歧（实现近似）。因此 `fountain.ts` 包含一个由精确指定的 IEEE-754 运算构建的确定性 log——V8 与 JavaScriptCore 的不同步是一种静默的、彻底的失败模式。

## 帧是自描述的

20 字节的头部携带会话 ID、序列号、块数量/大小、总长度和载荷哈希。没有握手：接收端可以中途锁定到一条流上，发送端重启（新会话 ID）会自动重置接收端。流标识覆盖*每一个*必须保持不变的头部字段，而不仅仅是会话 ID。

## 容器

在喷泉载荷内部，一个容器保存文件名、媒体类型、可选的 gzip（只在确实缩小载荷时应用），以及原始字节的 SHA-256。接收端通过容器的媒体类型区分文件和文本片段，并在提供任何东西之前校验 SHA-256。

## QR 层

纠错保持在 L：帧内 ECC 和喷泉解决的是不同问题（损坏 vs 擦除），在这个帧尺寸下，"整帧解码或丢弃"加上喷泉冗余是更好的取舍。掩码图案被钉死（任何声明的掩码对解码器都合法），跳过规范要求的 8 路掩码评估，生成速度快约 4 倍。

金标准线上格式向量在 `tests/` 里——编码器和解码器被约束到固定字节，而不只是彼此一致。
